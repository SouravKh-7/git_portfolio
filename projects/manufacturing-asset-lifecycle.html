01 · Problem

Equipment evidence is fragmented across systems and time.

Asset masters, sensor readings and maintenance work orders often disagree on identifiers, timing and status. A useful lifecycle view needs stable equipment identity, explicit event grain and visible rejection—not an opaque join that silently drops records.

Operational question

Which equipment needs attention, and what evidence supports that priority?

Decision boundary

The output supports maintenance review; it does not autonomously schedule work or claim failure prediction.

03 · Architecture

Preserve source evidence, create trusted lifecycle state, then serve decisions.

Boundary: the repository demonstrates the middle local path. The Bronze/Silver/Gold lane is an architecture direction and is not presented as deployed.

04 · Data flow

Batch today; incremental and event-aware later.

  1. Source snapshot
  2. Contract checks
  3. Valid / quarantine split
  4. Rule-based measures
  5. Consumer outputs

The current pipeline processes small, bounded CSV inputs in a documented sequence. A future incremental design would preserve event time and arrival time, use source watermarks or change versions, and define how late-arriving data corrects previously published state.

06 · Quality & reliability

Invalid data remains inspectable, and every metric keeps a qualifier.

Contracts

Validate identifiers, required fields, references, codes, dates and numeric ranges before trusted transformation.

Quarantine

Retain rejected payloads with a reason so correction and reprocessing can be designed instead of silently discarding data.

Reconciliation

Future tests should compare source, accepted, rejected and published counts and verify equipment coverage across stages.

Recovery

Target reruns need stable keys, checkpoints and idempotency before orchestration is added.

Availability currently uses a simplifying 30-day sample window. It is a project calculation, not a production SLA or measured operational result.

07 · Observability & operations

The next build must make data-product health visible.

  • Freshness: expected arrival and age by source.
  • Volume: accepted, rejected and published records by run.
  • Quality: rule outcomes, severity and recurring failures.
  • Lineage: source file or version through derived output.
  • Run state: start, completion, checkpoint, retry and owner.
  • Recovery: replay scope, correction procedure and evidence of restoration.

None of this production telemetry exists yet; it defines the acceptance criteria for the lakehouse phase.

08 · Performance

Scale claims require a baseline and a workload.

The current five-machine sample is evidence of logic flow, not throughput. A controlled experiment would hold the data and correctness checks constant while varying file size, partitions, join strategy and cluster configuration. Measures would include runtime, rows per second, shuffle, skew, small-file count and estimated cost.

09 · Serving

One trusted core, several consumer contracts.

Maintenance review

Equipment summary and priority output with the supporting measures and freshness timestamp.

Reliability analysis

Historical events and qualified metrics for trend and failure-mode exploration.

Operational API

A future read-only interface with versioned response schema, authorization and freshness metadata.

AI context

Only later: evidence-grounded retrieval over governed records, with recommendations separated from facts.

10 · Architecture decisions

ADRs make the tradeoffs durable.

ADR-001 · Accepted

Use stable equipment identity

Decision: join through asset_id, not mutable plant or line labels. Consequence: source mappings must reject or resolve unknown identifiers.

ADR-002 · Accepted

Quarantine instead of silent drop

Decision: keep malformed rows and reasons outside trusted outputs. Consequence: storage and reprocessing need explicit lifecycle rules.

ADR-003 · Proposed

Adopt Medallion responsibility boundaries

Decision: preserve Bronze evidence, conform in Silver and publish consumer-specific Gold products. Consequence: more tables and controls, but clearer replay and ownership.

ADR-004 · Deferred

Do not introduce ML before reliable labels

Decision: keep rule-based outputs while failure labels, leakage controls and an evaluation baseline are absent. Consequence: fewer predictive claims and stronger evidence discipline.

13 · What changes at scale

Volume changes the operating model, not only the engine.

Larger or continuously arriving telemetry would require distributed storage, partition and compaction policy, schema registry or enforceable contracts, workload isolation, cost controls, catalog and lineage, role-based access, tested backfills, monitoring, incident ownership, and explicit RPO/RTO targets. Those remain future work.
