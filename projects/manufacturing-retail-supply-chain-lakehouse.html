Manufacturing & Retail Supply Chain Lakehouse

A target Databricks architecture for connecting supplier, production, warehouse, inventory, sales and returns data without hiding their different grains, clocks and ownership boundaries.

01 · Problem

A supply chain is not one table or one clock.

Manufacturing, supplier, warehouse and retail systems use different identifiers, grains and update patterns. A trustworthy platform must preserve those differences, conform only what should be shared, and prove quantities across procurement, production, movement, sale and return boundaries.

Operational question

Where is product flow delayed, inconsistent or unavailable—and which source events support that conclusion?

Decision boundary

Gold products support analysis; the project does not claim live planning, optimization or automated replenishment.

03 · Target architecture

Sources remain traceable while conformed products earn trust.

04 · Ingestion & updates

Incremental by contract, replayable by design.

Source contract

Version schema, keys, cadence, semantics and ownership; classify compatible and breaking schema drift.

CDC

Carry source operation and offset/version metadata; test insert, update, delete and repeated delivery.

Time

Store event time separately from arrival time so delayed changes are visible.

Replay and backfill

Bound reprocessing by source version or date, use idempotent merge keys, and reconcile the affected publication window.

06 · Quality & reconciliation

Gold publication depends on business evidence, not only schema validity.

  • Structural: schema, required fields and type checks.
  • Identity: uniqueness and durable-key mapping.
  • Reference: product, supplier, location and order relationships.
  • Chronology: order, receipt, production, movement, sale and return sequence rules.
  • Quantities: non-negative and unit-compatible values with explicit exceptions.
  • Reconciliation: source-to-Bronze counts, accepted/rejected Silver totals and business flow balances.
  • Freshness: cadence-aware expectations by source and product.
  • Publication gate: fail closed for decision-critical mismatches.

No quality result exists yet; these are proposed test categories.

07 · Reliability & observability

Every run should explain what it processed and how to recover it.

Run identity

Source version, code version, parameters, checkpoint and affected interval.

Data health

Freshness, volume, rule outcomes, quarantine rate and reconciliation state.

Pipeline health

Task state, duration, retries, dependency status and ownership.

Recovery

Safe reset or replay scope, idempotency invariant and post-recovery reconciliation.

08 · Performance design

Partitioning follows workload evidence.

A future Spark lab would compare representative joins and aggregations while preserving correctness. It should capture input size, file count, partition size, skew, shuffle, spill, runtime and cost. Date/location partitioning, compaction, clustering and broadcast choices should be evaluated against query patterns, not described as universally optimal.

09 · Serving patterns

Products are shaped around consumers and freshness needs.

Supplier delivery

Order and receipt measures with comparable units, lateness rules and source coverage.

Production flow

Order, output and yield measures with plant, product and time context.

Inventory position

Movement-derived or reconciled snapshots with correction and freshness metadata.

Fulfillment, sales & returns

Transaction-grain facts and governed dimensions for cross-channel analysis.

A semantic layer could define shared measures. A read-only monitoring API is a possible future serving interface, but no API project is promoted here because there is no corresponding implementation evidence.

10 · Future API & AI monitoring boundary

Monitoring becomes a project only after the data foundation exists.

If implemented, endpoint groups would separate platform health, data-product freshness and quality, lineage/evidence, incident alerts, logs and metrics, model or rule versions, and audit history. Initial access would be read-only; authentication, role-based authorization, rate limits, immutable audit events and explicit deployment limits would be required before any write capability was considered. Any AI explanation would cite versioned evidence and remain outside write or remediation authority. This is a design boundary—not a fourth implemented project.

11 · Architecture decisions

ADRs connect the design to its consequences.

ADR-001 · Proposed

Keep source-aligned Bronze evidence

Decision: avoid early conformance in ingestion. Consequence: more storage, but safer replay and source-level diagnosis.

ADR-002 · Proposed

Separate event and arrival time

Decision: preserve both clocks through all layers. Consequence: models and tests must define late-data correction behavior.

ADR-003 · Proposed

Use idempotent merges for change processing

Decision: derive stable keys and source versions before merge. Consequence: deletion, out-of-order change and replay tests become mandatory.

ADR-004 · Proposed

Gate Gold on reconciliation

Decision: decision-critical products do not publish when required balances fail. Consequence: downstream availability may be delayed to protect correctness.

14 · What changes at scale

Domains, ownership and workload isolation become as important as throughput.

A larger platform needs catalog and lineage, domain ownership, producer/consumer contracts, environment isolation, access and privacy controls, streaming backpressure where used, storage lifecycle, cost budgets, workload classes, data-product SLOs, disaster recovery and change governance. These remain target-state requirements.
