01 · Engineering approach

How I Think About Data Systems

For each project, I begin with the problem and the expected decision. I then identify the source data, failure modes, quality risks, processing requirements, storage model, observability needs, and the final serving or decision layer. Only after the deterministic system works do I consider adding AI assistance.

01 · Contracts & sources

Define ownership before movement

Record grain, keys, schema, cadence, retention and producer expectations. A data contract turns assumptions into a versioned interface.

02 · Ingestion & change

Choose batch, streaming or incremental deliberately

Separate event time from arrival time; design for CDC, late data, replay, backfills and idempotent writes where the workload requires them.

03 · Storage & tables

Preserve evidence, then optimize access

Use Bronze, Silver and Gold boundaries, table formats and retention policies to balance traceability, usability, performance and cost.

04 · Data modeling

Make grain and history explicit

Define facts, dimensions, durable keys and SCD Type 2 history before transformations spread ambiguous meaning.

05 · Quality & reconciliation

Test the data product, not only the job

Apply contracts, rule severity, quarantine and source-to-target reconciliation. Publication gates should fail closed when decision-critical evidence is incomplete.

06 · Reliability & observability

Design recovery with the happy path

Expose freshness, lineage, run state, SLA/SLO health, retries, checkpoints and ownership so partial failure is diagnosable.

07 · Performance

Measure before tuning

Inspect partition sizes, skew, shuffle, cache behavior, query plans and concurrency. Publish a baseline, correctness check and repeatable comparison.

08 · Governance

Make trust operational

Lineage, catalog metadata, access control, privacy, retention and audit records define who may use a data product and under what conditions.

09 · Serving

Shape contracts around consumers

Tables, semantic models, APIs and features need distinct latency, compatibility and quality guarantees—plus a clear owner for change.

The architecture is not the starting point. It is the consequence of understanding the problem, data, risks, and decision boundary.

Architecture principles

Six rules I use to make design decisions visible.

These are working principles, not claims of universal best practice. Each one creates a testable question for the project.

01

Contracts before pipelines

Define grain, keys, cadence, ownership and failure behavior before implementation hardens hidden assumptions.

02

Idempotency before automation

A retry or replay should converge on the same valid state before orchestration makes it easier to run repeatedly.

03

Observability before scale

Establish evidence for freshness, volume, quality, lineage and failures before multiplying data or compute.

04

Reconciliation before trust

A successful task is not proof of a complete output. Compare counts, keys and business quantities across boundaries.

05

Ownership before platform sprawl

Every data product needs a producer, consumer, support path, change policy and retirement decision.

06

AI after reliable data foundations

Models may interpret evidence; they should not repair missing provenance, bypass access policy or invent operational truth.

Data architecture lens

Architecture spans structure, flow, ownership and time.

Domain boundaries

Separate equipment, maintenance, incident and supply-chain contexts; define where shared identifiers and conformed entities are justified.

Data products & ownership

Treat curated outputs as supported interfaces with named producers, consumers, contracts and deprecation paths.

Metadata & lineage

Keep source, transformation, run, schema and quality context close enough to reconstruct how a result was produced.

Event versus batch

Use event-driven flows for responsiveness only when ordering, replay and operating cost are understood; use batch when simpler freshness is sufficient.

Historical modeling

Distinguish current state, event history and correction history so late-arriving changes do not silently rewrite the past.

System design notes

Small records of the decisions behind a reliable platform.

Each note is intentionally short today and can grow into a benchmark, ADR, diagram or failure experiment later.

Batch versus streaming

Start with the consumer freshness requirement. Streaming adds ordering, state, replay and continuous operating concerns; it is justified only when batch latency misses the decision window.

CDC and incremental loading

Track source offsets or watermarks, operation type and ingestion metadata. Make merges idempotent and test inserts, updates, deletes and repeated delivery.

Late-arriving data

Preserve event time and arrival time, define a correction window, and specify when previously published aggregates are recomputed.

Partitioning strategy

Partition for pruning and manageable file sizes, not for every filter. Measure skew, small files and write amplification using the real query pattern.

SCD Type 2

Use effective intervals and a current marker where historical attribute state matters. Guard against overlapping versions and out-of-order changes.

Idempotency

Derive stable business or event keys, record run identity, and design reruns so a partial failure can be retried without duplicating valid state.

Schema evolution

Classify additive, compatible and breaking changes. Quarantine unexpected payloads and version consumer contracts before changing published structures.

Data contracts

Combine machine-readable schema and checks with human ownership, cadence, semantics and incident expectations.

RPO and RTO

Translate business tolerance into maximum acceptable data loss and restoration time, then test recovery procedures against those targets.

Bronze, Silver and Gold

Use layers as explicit responsibility boundaries: reproducible source evidence, conformed trusted records, and consumer-shaped products.

Environmental & Health-Aware Drone Fleet Intelligence

When does the geographically shortest mission stop being the safest, most energy-efficient, most reliable, or most productive mission?

A trusted data plane combines inspection priority, weather, battery reserve, component health, communication, fleet workload, and route constraints. Deterministic planners and simulation establish feasibility; a bounded agent may retrieve evidence, call approved tools, and explain trade-offs without controlling the flight stack.

Control boundary

Generative intelligence may propose and coordinate. Deterministic systems establish feasibility and enforce low-level safety.

  1. Verify mission, asset, fleet, and environmental inputs.
  2. Generate assignments and route candidates.
  3. Evaluate energy, weather, health, communication, and timing in simulation.
  4. Apply policy and human review before publishing a mission plan.
  5. Return telemetry and inspection evidence to measurable business outcomes.
